## Befunde

1. **PROZESS_SUCHE P2 „mehrere Sessions“ (Testfehler, behoben):** Die drei Requests C1–C3 laufen nacheinander als Jobs und können im selben Job-Slave landen, in run 2532 alle drei mit derselben SID. Die Prüfung steht jetzt in P6, wo sechs Jobs gleichzeitig laufen (run 2548: je Runde 6 Sessions).
2. **RUECKSCHREIBUNG und LOGTEXT_GRENZEN im SERVER-Modus (Folge von PROZESS_SUCHE, behoben):** PROZESS_SUCHE setzt in der aufrufenden Session den Dispatcher `LT_DISP` und hob ihn am Ende nicht auf. Die folgenden Skripte liefen in derselben SQLcl-Session; ihr `SERVER_NEW_PROCESS` ging an den gestoppten Dispatcher und endete mit `PROCESS_TIMEOUT` (13 Einträge in `LILAM_LOG_INTERNAL`, belegt). SPEICHER hebt die Einstellung aus demselben Grund schon auf (U-Bahn-Simulation, run 2034). PROZESS_SUCHE ruft jetzt am Ende und im Fehlerfall `set_dispatcher_pipe(null)` auf.
3. **SPEICHER run 2547, SV „Alle Logs“ 27996/28000 und „Alle Prozesse geschlossen“ 6999/7000 (Ausreißer unter Last):** Ein Worker holte ein `NEW_PROCESS` erst nach Ablauf der 3 s ab und verwarf es (`doRemote_newProcess`, EXPIRED); der Client erhielt `PROCESS_TIMEOUT`, seine 4 Logs gingen an die ungültige ID. Das ist das vorgesehene Verhalten bei einer Zeitüberschreitung. Der SERVER-Modus nutzt den neuen Code nicht, und in run 2551 und 2552 trat es nicht wieder auf. Die beiden CHECK-Constraint-Einträge (`LT_SPM_LOG_CK`) erzeugt der Test absichtlich.
4. **SPEICHER run 2551, „SV PGA des Clients“ Median 115 B (Grenze 100 B; Messausreißer):** Blöcke 106, 0, 115, 278, 131. Mit demselben Package lag der Wert in run 2547 und 2552 bei 0 B, ebenso in allen Läufen seit 05.10. Die PGA wächst in 64-KB-Schritten (siehe CLAUDE_ANWEISUNGEN 7.1); der neue Code läuft im SERVER-Modus des Clients nicht. Vermutung: Messrauschen in einer Session, die vorher PROZESS_SUCHE ausgeführt hatte; nicht weiter untersucht.

## Fazit

Die neuen Funktionen und die `CALL_BY_JSON`-Korrektur verursachen keine Regression: Alle Tests sind ohne Änderung an LILAM bestanden, die beiden Fehler im Hauptlauf gingen auf den neuen Test zurück und sind dort behoben. Ein bestehendes Verhalten wurde dabei sichtbar: Eine Session mit gesetztem, aber gestopptem Dispatcher schickt `SERVER_NEW_PROCESS` weiter an ihn und wartet jeweils den Timeout ab. Im APEX-Betrieb ist das erwartbar, im Testbetrieb muss jeder Test die Einstellung aufheben.
