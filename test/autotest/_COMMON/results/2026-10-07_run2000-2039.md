## Befunde

### 1. Neu gestarteter Server beantwortet kein `SERVER_NEW_SESSION` (nicht reproduziert, produktionsrelevant falls echt)

Run 2034, SERVER-Teil: Der Test startet `UB_S1` (Gruppe `SUBWAY`) per `CREATE_SERVER` und wartet mit `lt.wait_servers_ready`, bis er registriert ist („Server bereit: 1/1“). Alle vier folgenden `SERVER_NEW_SESSION` (13:39:18–13:39:30) endeten nach je 3 s mit `NUM_ERR_SESSION_TIMEOUT` (−20110; vier Einträge „Could not establish connection to LILAM-Server: TIMEOUT“ in `LILAM_LOG_INTERNAL`, ID 103–106). Folgeprüfungen U2–U9 fehlten daher. Der Server lief dabei weiter (Job `UB_S1` 13:39:17–13:40:15) und beantwortete am Ende das `SERVER_SHUTDOWN` über die Daten-Pipe ordnungsgemäß. Die Anwendung war, wie vorgesehen, nicht betroffen (negative IDs, keine Exception), die Daten der vier Prozesse gingen aber verloren.

Unmittelbar davor lief SPEICHER (2033) in derselben SQLcl-Session; dessen Server `LT_S1`, `LT_S2`, `LT_DISP` waren 13:39:13–13:39:16 gestoppt. In den Wiederholungen 2036 und 2038 (ohne SPEICHER davor) bestand der SERVER-Teil, ebenso in run 1995.

**Ursache:** nicht belegt. Die Serverauswahl (`getServerPipeAvailable`) liest nur die Registry nach Gruppe; ein Verweis auf die gestoppten LT-Server ist damit unwahrscheinlich. Vermutung: `NEW_SESSION` geht über die Steuer-Pipe `UB_S1_CTL`, `SHUTDOWN` über die Daten-Pipe; der Server las in den ersten Sekunden nach dem Start die Steuer-Pipe nicht oder verwarf die Anfragen (z. B. als verfallen, `expires_utc`), während die Daten-Pipe funktionierte.

**Vorschlag:** Auf Freigabe gezielt nachstellen (SPEICHER oder ein Server-Stopp unmittelbar vor `CREATE_SERVER` eines neuen Servers und sofortigem `SERVER_NEW_SESSION`), dabei die Steuer-Pipe und die Ablehnungsgründe des Servers mitprotokollieren. Kein Code geändert.
